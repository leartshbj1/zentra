## Decision

It closes a real workflow gap after clients/devis/invoices/receipts/purchasing/manual journals/periods. It does not require a bank provider, a tax provider, a different accounting method, public provisioning, projects or orders.

Use the existing pure reconciliation rules on `projectUsFinancialBookV5(book).ledger`. Persist the review facts in a narrowly scoped TEST sidecar bound transactionally to that existing V5 financial head. This sidecar is a statement/approval register, **not a second ledger or a new financial engine**: import/match/complete/void do not create a financial event, change a journal, settle an invoice, or advance the financial revision. Its own review revision must be explicit. Do not add a new no-posting financial event family merely to trigger polling; that would expand every kernel replay/validator and SQL append profile without adding a financial effect.

## Scope and accounting meaning

1. Show the current US/USD/accrual pilot cash account and statement history. Import a deliberately chosen CSV with explicit start/end/opening/closing; display a preview and totals before the human approves saving it. The browser uses the existing strict parser, then submits canonical row facts; the server independently validates all rows/balances and derives IDs/authority. SQL independently validates and binds those same canonical facts. Raw file formatting is not an authoritative request or persistence source.
2. Show unmatched statement lines and current ledger cash movements in that date range. Human selects one or several whole statement lines and one or several whole journal movements, reviews signed totals, and approves only exact equality.
3. Display outstanding lines, unmatched book movements, opening difference, closing difference and readiness. Completion is an immutable approval of this exact current ledger/review state. Void requires a reason and is limited to unused uncompleted statements, as today.
4. Export the complete reconciliation as CSV, containing scope/revisions, statement dates/balances, canonical lines, grouped match relations with public journal revisions, signed movements, current differences, completion details and any current-vs-completed warning. No silent truncated export.
5. Missing fees/adjustments are recorded explicitly through the existing manual journal workflow, then reviewed and matched. Matching itself never manufactures an entry or records a customer/vendor payment. A statement line with a real settlement must first use the corresponding existing payment flow.

Here, "cleared" means a whole existing cash journal is included in an approved match. It does not assert bank settlement finality or implement an account-level clearing subledger. This small workflow intentionally keeps the current exact-coverage completion rule; realistic outstanding cheque/deposit timing schedules, partial movement allocations and adjustments require a later domain decision. Do not rename this narrow rule to claim a universally complete bank reconciliation product.

## Concrete API and public domain boundary

New namespace: `/api/international/workspaces/[organizationId]/financial-pilot/bank`.

| Route | Bounded behavior |
| --- | --- |
| `GET /head` | Cheap composite head `{consumer:'financial-pilot',schemaVersion:1,organizationId,revision,bankRevision}`; `revision` is the existing financial head, `bankRevision` is the bank review head. It does not aggregate the full book. |
| `GET /context?revision=F&bankRevision=B` | Current admitted cash accounts and import readiness, including a precise legacy-pending blocker. No routing/account number, provider connection, grant, policy or private source. |
| `GET /statements?revision=F&bankRevision=B&cursor=...` | 25 safe statement summaries per page, deterministic order. Cursor binds tenant, both heads, kind and scope. |
| `GET /statements/[id]?revision=F&bankRevision=B&lineCursor=...&matchCursor=...` | Safe immutable metadata/status/differences; statement lines and approved match groups paginated in groups of 25. A grouped match still has validated bounded sets, not an unbounded nested document. |
| `GET /statements/[id]/movements?revision=F&bankRevision=B&cursor=...` | 25 true-ledger candidate cash movements: public `journalRevision`, dates, signed minor units, safe source/description, current claimed state. Filter on payment/transaction date. No entry ID/fingerprint/idempotency key. |
| `POST /operations` | Exactly four actions below; own-data closed JSON, body/decoded text/structural budgets. Current pilot marker, expected-user and same-origin admission. |
| `GET /statements/[id]/export?revision=F&bankRevision=B&statementRevision=R&format=csv&language=en` | Complete validated bank export snapshot; byte bound, no-store attachment, selector/content hashes and both heads rechecked after rendering. Languages FR/DE/IT/EN; exact USD decimals and ISO document dates. PDF is deferred. |

Public request envelope: `{consumer:'financial-pilot',schemaVersion:1,requestId:<UUID>,expectedRevision:F,expectedBankRevision:B,expectedStatementRevision:null|R,command}`. Financial F >=1; bank B >=0; new statement revision starts at 0. Commands:

- `create_statement`: `{type,cashAccountId,start,end,openingMinor,closingMinor,lines:[{date,amountMinor,reference}]}`. UI opening/closing and CSV amounts are explicit decimal USD strings parsed with the existing strict parser; the public request contains signed minor-unit strings and original row order. Statement UUID = requestId; line IDs = `<statement UUID>:<original row index>`; `externalConnectionId` is the fixed private opaque manual marker, never a provider credential. No organization/currency/actor/private ID comes from imported rows. Canonical rows are untrusted request facts, independently revalidated by the server and SQL, not trusted evidence or calculated status.
- `approve_match`: `{type,statementId,statementLineIds,journalRevisions}`. Capture/sort/deduplicate sets before hashing. Server resolves the numeric true-ledger revisions to private IDs and uses match UUID = requestId. Never use compatibility(), array indices or old ERP records to resolve them.
- `complete`: `{type,statementId}`.
- `void_statement`: `{type,statementId,reason}`.

Use private key `pilot:bank:<requestId>`. Hash the exact captured canonical public request with organization and admitted actor; SQL recomputes the same canonical hash. Original canonical row order/references remain in that retry envelope, while duplicate-content detection uses validated statement facts without artificial IDs. Store only canonical lines, not raw CSV file/text. SQL receives the captured public request as well as the proposed record/receipt: it reconstructs the canonical import from that record, derives IDs/marker, and compares every row and metadata field with the request. For matching it resolves each requested journal revision against the true ledger and verifies the exact sorted private-ID set; completion/void compare their exact source and reason. Thus no raw-text-to-canonical-payload gap is hidden behind the request hash, and no second SQL CSV parser is required. Public receipts whitelist requestId/action/statementId, original financial revision, resulting bank revision and statement revision; they do not expose actor hash, private key, stored book fingerprint or replay internals.

Receipt-first applies under fresh current authority, even after either head has advanced: exact key/request/actor/action/entity comparisons return the original receipt without resolving a changed source or reapplying a transition. For a new operation, compare both expected heads, then resolve current sources, transition and commit. If a receipt can have committed between a probe and a source-dependent rejection, re-probe once before rejecting. At most one bounded exact retry after a conflict; no new UUID, replaced expected revision, automatic amount adjustment or hidden rebase. A late access error may withhold an already committed receipt; the pending request must remain recoverable.

## Risks and explicit exclusions

- **Timing differences:** the reused domain requires exact coverage and cannot close with conventional outstanding-item schedules. Preserve this honest limitation rather than inventing behavior or legal conclusions.
- **Single cash account / global whole-journal claim:** matches current starter chart and existing bank rule. Multiple bank accounts, transfers, splitting one journal across accounts/statements or allocating partial payment amounts need a different claim model.
- **Volume:** bounded aggregate reads and full canonical statements are suitable for this private pilot only. Durable high-volume pagination, raw source archival/retention and historical amendment are separate work.
- **Authority:** Auth/D1 and PostgreSQL retain separate pre/post fences; no distributed transaction, SLA or universal immediate revocation is claimed. The server role remains trusted and must not issue its own grants.
- **Regulatory/provider claims:** the planning agent made no new legal claims. Official sources were subsequently checked by the parent and are listed in the mandatory addendum below. US record retention, documentary requirements, state/federal tax basis, GAAP suitability, outstanding-item policy and connected-bank obligations remain **research and professional review needed** before a real launch. ### 1. Identités et canonisation fermées

Les UUID de relevés sont réservés **dans l'union legacy + nouveau**, y compris les anciens relevés annulés. La création rejette toute collision d'UUID sous le verrou du tenant avant écriture. Aucun lookup ne choisit arbitrairement l'origine nouvelle, aucune mutation legacy et aucun fallback vers un reçu ERP4. L'origine figure dans les résumés, détails et exports.

La collision de contenu utilise les mêmes faits canoniques dans les deux origines : compte cash, dates, soldes et lignes ordonnées. Ne pas comparer aveuglément les anciens hashes de contenu, l'identité TS qui inclut le tenant et le nouveau hash de requête qui inclut aussi acteur/attentes/UUID : leurs domaines sont différents. SQL compare ou recalcule une recette de contenu commune à partir des records validés.

Marqueur manuel opaque fixe : `manual-csv:financial-pilot-v1`. ID du relevé = UUID requestId ; IDs des lignes = `<UUID>:1`, `<UUID>:2`, etc., dérivés serveur et SQL. Montants signés canoniques en minor units ; aucun float, `-0`, exponentiel ou coercition. Les doublons de sélecteurs de match sont refusés. Les ensembles uniques sont triés avant revue/hash : journalRevisions numériquement, statementLineIds selon UTF-16 ; les IDs privés résolus sont triés selon UTF-16 comme le moteur existant. Le contrat et SQL doivent prouver exactement la même normalisation. Les lignes de relevé gardent ordre, références et caractères exacts, sans trim, normalisation Unicode ou tri silencieux.

Le hash SHA-256 utilise le sérialiseur canonique existant sur tenant + userId admis + requête publique canonique complète. Il atteste les faits relus, pas les octets wire JSON ni l'authenticité d'un CSV bancaire. Le serveur et SQL dérivent tous les IDs et comparent chaque fait canonique au record proposé. Aucun parser CSV SQL n'est ajouté ; aucun CSV brut n'est conservé implicitement.

### 2. Preuve durable par opération et reprise prioritaire

Chaque reçu/audit immuable conserve **la requête publique canonique complète**, actorId, instant, clé dérivée, action/entité, F attendu original, B attendu original, R attendu original (null à l'import), B/R résultants, hash, F source, SHA du préfixe source et vraie révision L. Ces données sont privées. Une approbation antérieure ne dépend pas d'un unique hash mutable dans le dernier record. Les bornes s'appliquent aussi à ces preuves ; aucune lecture ne les agrège sans limite.

SQL reconstruit le préfixe du vrai livre à ce F, corrobore SHA/L, retrouve les journaux déjà présents et prouve le mapping exact entre journalRevisions publics, IDs privés, dates, cash et montants. Un bundle record/reçu/audit/claims cohérent mais falsifié doit être refusé, notamment si son entrée n'existait pas encore à F. Aucun second ledger ou snapshot financier mutable n'est persisté.

Ordre : capture canonique → autorité courante → hash actor/requête → reçu exact corroboré → seulement en absence de reçu, CAS F/B/R et éligibilité actuelle → transition → commit. Un replay exact reste valide après clôture, annulation, nouvelle écriture, autre rapprochement ou nouveau blocker legacy. Il exige l'autorité vivante du demandeur actuel mais ne réadmet pas les anciens approbateurs pour valider l'histoire. L'historique reste lisible par un acteur autorisé différent après départ de l'approbateur d'origine. Aucun rebase, nouvel UUID ou remplacement des attentes sur reprise. Re-probe unique et reprise bornée comme décrits plus haut ; erreur tardive ou réponse incertaine conserve l'enveloppe exacte en RAM.

### 3. Invariants SQL et révisions distinctes

Ordre de verrouillage : **workspace → country → ERP head → grant → pilot opt-in → financial cursor → banque/history/claims**. F/B est capturé dans une seule transaction admise. Les guards de DML directs corroborent le même tenant/source, y compris si une inversion de verrous doit faire échouer la transaction. Aucun session flag ne remplace ces contrôles. Pas de preuve multiconnexion dans PGlite.

B=0 si l'audit nouveau est vide ; toute action nouvelle alloue exactement B+1 sous le verrou existant. L'audit a positivité/bornes, unicité tenant/B, séquence complète 1…B et une corrélation exacte de chaque B avec reçu, transition de record et delta de claims. R commence à0 puis avance d'une unité par action. Les actions import/approve/complete/void ne changent ni livre, événements, reçus financiers, cursor/hash, ledger, comptes, paiements ou baseline ERP. Les faits importés, approbations et preuves précédentes sont immuables ; UPDATE/DELETE/TRUNCATE des historiques sont refusés.

Les noms F (finance), L (vrai ledger), B (banque du tenant) et R (relevé) ne sont pas interchangeables. L inclut les audits de périodes ; F et L peuvent avancer différemment ; B avance seul lors d'une revue. Le reçu renvoie F original inchangé et B/R résultants. Aucun journal n'est résolu par F, index de tableau ou révision de compatibilité. Bornes safe integer et refus d'overflow dans TS/SQL. La revue a confirmé qu'un jalon réduit à huit fichiers sans handlers est cohérent ; le présent plan retient douze fichiers en ajoutant explicitement les quatre fichiers serveur/bindings et leurs tests, afin de vérifier aussi leurs fences sans monter de routes.
