## One country-specific admission, same ERP authority

Keep CH session/licence/approval/resolution behavior unchanged. US admission uses the existing ready workspace, US membership and USD SaaS authority, with a fresh member-seat check. New challenge/session records contain credentials, not another financial book or subscription. US secrets never satisfy a CH bearer/licence reader. No US membership is copied to CH tables.

All new protocol responses use `protocol: 'zentra-us-device-v1'` and `edition: 'us_experimental'` on successful connected metadata. Country is US and currency USD. Client maximum schema is explicit 1/2/3; the initial native client announces 3. It does not grant higher server capability or bypass purchasing/projects flags.

Fixed API routes under `/api/international/device`: `start`, `approve`, `exchange`, `me`, `revoke`. Approval page is `/appareil/us`. There are no credentials in URLs, logs or exports. No redirects or automatic POST retries. A lost exchange is recovered only by exact replay of the same protected pending body.

## Exact DTOs

- Start POST: `{protocol, installationId, sessionTokenHash, supportedSchemaVersion}`. Installation is a real canonical UUID v4. Hash is canonical base64url SHA-256, 43 characters, of UTF-8 `zentra:us-device-session:v1:${token}`. Native mints a 32-byte cryptographic `zus_` token and retains it in protected pending state before the request. Server stores only its hash. Response 201: `{protocol,deviceCode,userCode,verificationUri,expiresAt,interval,supportedSchemaVersion}`. `deviceCode` is a cryptographic `zud_` token with 43 base64url characters; userCode uses the existing eight-character human code, formatted `XXXX-XXXX`. Verification URI is fixed to `https://zentraapp.ch/appareil/us?code=...`; lifetime 600 seconds, interval 3 seconds. A lost start can be restarted; unused challenges expire and grant nothing.
- Approve POST: `{protocol,userCode,organizationId}`. Browser-only fresh Auth and same-origin check, explicit selected US company; never choose the first of several companies. Response `{protocol,approved:true,organizationId,organizationName,country:'US',currency:'USD'}`. This acknowledgement is not a credential or financial permission.
- Exchange POST: `{protocol,deviceCode,installationId,sessionToken}`. The token's namespace, canonical form and hash must match the start record. Pending response 202: `{protocol,status:'authorization_pending'}`. A connected response is the exact metadata below, without returning or persisting the bearer in clear text. Atomic consumption/session insertion and exact idempotent replay are required; a different token/install/company cannot adopt the challenge.
- Connected metadata (exchange and GET me): `{protocol,edition:'us_experimental',status:'connected',sessionId,organizationId,organizationName,userId,installationId,role,subscriptionId,country:'US',currency:'USD',expiresAt,entitlementValidUntil,supportedSchemaVersion}`. IDs/user/install are explicit and validated; session ID is `usd_` plus UUID v4. Times are safe nonnegative Unix seconds. Expiry is bounded by the approved authority and 30 days. Fresh configuration and authority must remain US/USD. No CH licence is included.
- Revoke POST: Authorization only (optional exact `{protocol}` body). Result `{protocol,revoked:true}`. It remains possible to revoke the matching credential when entitlement or feature flags close; do not require an active subscription to log out. Unknown tokens remain unauthorized. Revoke is idempotent for the same matching token.

Token hash purposes are distinct: session prefix above; device code UTF-8 `zentra:us-device-code:v1:${deviceCode}`. Neither accepts old `zds_`/`zdv_` credentials. The client chosen bearer is generated by the real native cryptographic source, not a user password or UUID. Server limits body sizes and attempts. Device credentials are opaque access credentials; roles and subscription rights always come from fresh server records.

## Authorization and races

`INTERNATIONAL_US_NATIVE_ADMISSION_ENABLED=true` is additionally required for new admissions and reads/writes, alongside existing core/US ERP flags. All default closed. Recheck flags, browser identity, ready creation, membership, USD offer/evidence, seat occupancy, country configuration, expiry and revocation around every awaited operation and protected result. SQL commit fences must not rely only on an earlier JavaScript check. Lost commit response may recover the identical admission; different approved identity/role or challenge cannot replay it.

`requireUsDeviceSession(request, allowedRoles?)` chooses only US bearer authority. It never falls back to cookies or CH sessions. ERP, seller/tax/export bindings use it for native Authorization; country routes explicitly dispatch by credential family and preserve CH behavior. A role change invalidates the original native context rather than granting a new role to an old draft.

Native stores a separate typed protected US session and pending state, plus an explicit selected-edition reference and anti-race context. CH protected formats stay exact. Snapshot/read/head/delta/execute use the same US stamp before and after both successful and failed network outcomes; no lock is held while waiting for the network. The stamp is based on US protected session/selection revisions and nonce, never fake CH Automation/Notes bindings.
