# Support — daily work

Mode: Operate. Extend the existing Studio folder/list/reading interface, without changing its identity.

THESIS: Show what needs attention and let the team act on several proposals without losing control of recipients or decisions.
STORY: A short daily record above the inbox; sender protection and a follow-up beside the message; selection tools only in Démarchage; shared rules and connection checks in settings.
FORM: Existing typography, forest accent, white reading surface and fine separators. No new dashboard grid. Mobile keeps a single reading pane, wraps actions and opens batch replies as a vertical editable list.
TRUTH: Counts come from stored events. Rules are explicit company preferences, not model retraining. Ignoring never deletes provider mail. Every outgoing reply remains editable and requires confirmation. Provider acceptance never claims delivery.
FINISH: Test tenant boundaries, concurrent changes, actual counts and partial batch outcomes; inspect desktop and narrow mobile views. Preserve PRODUCT.md and DESIGN.md.

## Implemented scope

The extension lives in `components/support/productivity-panel.tsx`, with integration in `components/support/application.tsx`, local demonstration behavior in `components/support/productivity-demo.ts`, and surface styles in `app/support/support.css`. Server behavior is defined by `lib/support/sender-policies.ts`, `followups.ts`, `productivity.ts`, `batch.ts` and their guarded dispatch in `service.ts`.

- **Daily record:** a short paragraph above the inbox when no category or state filter is active. Automatic classification totals count distinct tickets with stored `routed` or `quiet` events attributed to Zentra Support during the Europe/Zurich calendar day, including daylight-saving boundaries. The quiet count is a subset. Messages to verify are the current `review`/`error` backlog, not a count restricted to today. Gestion shows today's completed invoice and appointment imports plus its current pending backlog only for an authorized linked company with the required entitlement; no accounting documents are exposed here. Open reminders and reception details sit behind “Suivis et réception”.
- **Explicit company preferences:** administrators add, edit, activate, deactivate or delete rules shared only within the selected Support workspace. Rules use a connector-provided sender address and an optional normalized subject fragment; message body addresses are not used. “Mémoriser ce classement” opens an editable preference before saving. These preferences guide subsequent automatic classification and do not retrain a model. Conflicting rules and attempts to set aside important messages remain review cases.
- **Trusted senders:** “Protéger cet expéditeur” opens an explicit all-subject trusted-sender preference. A trusted sender cannot be automatically hidden as solicitation or spam by these policies; a would-be hidden message returns to a visible review case. “Ce n’est pas du démarchage” separately corrects the current ticket, with revision and processing guards. Neither action deletes provider mail.
- **Grouped actions:** Démarchage exposes selection from the displayed list, grouped by sender, with a server-enforced limit of 20 tickets. Ignoring records an internal disposition while retaining messages in Zentra and the provider mailbox. STOP preparation produces a vertical series of bordered editors with visible To/From, editable subject and text, and a review checkbox per sendable reply. Editing resets that reply's review. Duplicate recipients are suppressed in the preview and guarded again during server submission; final sending requires explicit confirmation. Individual authorization, recipient, revision/fingerprint and idempotency guards are reused, with per-item results when only part of a batch succeeds.
- **Assigned follow-ups:** solicitation messages can receive a title, responsible member and future reminder date. The optional Gestion task requires an enabled company link, Automation entitlement, a writable actor role, and active writable company membership plus an available member seat for the assignee. A linked task's state comes from Gestion and is completed through its Automation link; a Support-only follow-up can be completed in Support. Creation is idempotent for a ticket version. Reminder navigation can load an authorized target ticket beyond the initial 60-ticket list.
- **Connection checks and reply truth:** Connexions distinguishes the last verification or synchronization from the last message actually received in Zentra. Administrators can check supported non-API connections; Infomaniak uses mailbox synchronization, other supported connections verify access, and an API connection waits for an incoming event. A successful check does not prove that every expected message arrived. A reply in `accepted` state is labeled accepted by the mail provider, with delivery explicitly unconfirmed; uncertain submissions remain distinguishable.

## Visual implementation

The folder/list/reading structure and incumbent Studio identity remain intact. The daily record, shared preferences and connection rows use the existing white and pale neutral surfaces, forest accent and thin separators, without a new card dashboard or added shadows. Daily headings use 1.2rem, section headings 1.4rem, and batch/connection subheads 1rem at weight 600; these are local surface roles, not additions to the global type tokens.

The daily paragraph is limited to 72ch. Settings sections cap at 780px and grouped work at 820px. Controls wrap, disclosures and check rows retain a minimum 44px height, and the batch text editors reuse the established white field treatment, 9px corners and 160px minimum height. At 600px and below, paired fields and rule/connection rows become single-column, editable fields use 16px text, and long addresses wrap. Existing mobile reading behavior continues to show one pane.
